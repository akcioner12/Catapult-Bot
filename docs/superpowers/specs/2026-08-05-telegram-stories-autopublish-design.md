# Telegram Stories Autopublish — Design Spec

## Executive Summary
Каждое видео, которое пайплайн уже публикует на YouTube/TikTok/Instagram, дополнительно публикуется в Stories Telegram-канала `@Crypto_AI_Forex` — в тот же момент, автоматически, без ручного шага. Цель — использовать Stories как ещё один канал привлечения подписчиков, задействуя контент, который и так уже производится.

## Problem Statement
Пайплайн генерирует видео 2 раза в день и публикует их на YouTube, TikTok, Instagram Reels. Telegram Stories канала — неиспользуемый ресурс с потенциалом приводить подписчиков напрямую в канал, но нет механизма туда публиковать.

## Почему это не тривиальная задача (ключевая находка ресёрча)
Обычный Bot API **не поддерживает публикацию Stories в канал** — метод `postStory` работает только для персональных Business-аккаунтов (см. [core.telegram.org/bots/api](https://core.telegram.org/bots/api)). Публикация от имени канала возможна только через полный MTProto API (`stories.sendStory`), авторизованный как реальный пользовательский аккаунт с правом «Post stories» в этом канале — это открытый нерешённый feature request в `tdlib/telegram-bot-api` (issue #588).

Дополнительно: количество сторис/день у канала ограничено уровнем **буста** канала (Level 1 = 1 сторис/день, +1 за каждый следующий уровень; порог — ~1 буст на 250 подписчиков, округление вверх). У пользователя уже оплачен Telegram Premium (даёт 4 буста) — назначение их каналу вне зоны ответственности кода, делает сам пользователь в приложении Telegram.

## Success Criteria
- Каждое опубликованное видео (все категории, без исключений) появляется в Stories канала в течение той же минуты, что и остальные площадки.
- Публикация полностью автоматическая, без одобрения.
- При сбое — админ получает уведомление и может вручную повторить попытку.

## User Journey
1. Видео проходит обычный путь: генерация → YouTube upload → `_finish_publish()`.
2. Внутри `_finish_publish()` (после YouTube, параллельно с TikTok/Instagram) — новый шаг: публикация в Stories.
3. При успехе — просто попадает в общую сводку `"Видео опубликовано:"`, дополнительная строка `✅ Stories: <ссылка>` (если Telegram даёт ссылку на сторис) или просто `✅ Stories опубликовано`.
4. При сбое — строка `⚠️ Stories не удалось (<причина>) — /retry_story <video_id>`, видео сохраняется в `story_retry_pending` (аналог `tiktok_retry_pending`).

## Функциональные требования

### Must Have (P0)
- Новый модуль `subagents/telegram_story_publisher.py`:
  - `post_story(video_path: str, caption: str, link_url: str) -> tuple[str | None, str | None]` — публикует видео в Stories, возвращает `(story_url_или_None, причина_ошибки_или_None)`. Никогда не бросает исключение (паттерн как у `buffer_publisher.publish_to_buffer`).
  - Клиент Telethon инициализируется из `TELEGRAM_SESSION_STRING` (Railway secret) + `TELEGRAM_API_ID`/`TELEGRAM_API_HASH` (получаются пользователем на my.telegram.org — привязаны к номеру телефона, не то же самое, что Bot API токен).
  - Story-caption: короткое описание (первая строка/предложение уже сгенерированного YouTube-описания, без отдельного вызова Claude) + список остальных соцсетей текстом. Telegram-канал — единственная кликабельная ссылка-стикер (через `media_areas`/`MediaAreaUrl` в `stories.sendStory`) — **точный конструктор уточнить в момент реализации**, это risk-пункт ниже.
  - Видео дольше ~60 сек — обрезать до 60 сек перед отправкой в Stories (платформенный лимит) либо пропустить с уведомлением, если обрезка не имеет смысла для контента.
- Хук в `subagents/yt_publisher.py::_finish_publish()` — вызов `post_story()` для всех категорий без исключений, сразу после/параллельно с TikTok-веткой.
- `story_retry_pending: dict` + `save_story_retry_pending()`/загрузка при старте (копия существующего паттерна `instagram_retry_pending`).
- Команда `/retry_story <video_id>` в `parser.py` (копия `/retry_instagram`).
- Одноразовый локальный скрипт логина (Telethon `StringSession`) — генерирует `TELEGRAM_SESSION_STRING`, пользователь запускает один раз локально, вводит код из Telegram, я переношу результат в Railway variables.

### Should Have (P1)
- Если Telegram вернёт ошибку «недостаточно буста / сторис не разблокированы» — отдельное, понятное сообщение админу (не просто generic "не удалось"), чтобы сразу было ясно, в чём дело, а не путать с сетевым сбоем.

### Out of Scope
- Ручное одобрение перед публикацией в Stories (решили — полностью автомат).
- Отдельная генерация текста под Stories через Claude (переиспользуем существующий).
- Множественные клик-стикеры / несколько ссылок в сторис (платформа не поддерживает).
- Ограничение по категориям (catapult/forexbot) — Stories не имеют своей compliance-проверки типа TikTok, но и не Instagram — риск блокировки аккаунта Telegram за финансовый контент отдельно не обсуждался и не выявлен как проблема (в отличие от Meta/TikTok), поэтому осознанно не фильтруем.

## Технические риски / открытые вопросы для реализации
1. **Точный API-вызов для кликабельного стикера-ссылки** (`media_areas` в `stories.sendStory`) — нужно свериться с актуальной MTProto-схемой Telethon в момент написания кода, самим ресёрчем по названию класса не подтверждено на 100%.
2. **Риск для личного аккаунта** — автоматизация через MTProto (не Bot API) может попасть под антиспам-эвристики Telegram при слишком частой/шаблонной активности. Пользователь осознанно принял этот риск.
3. **Буст-уровень канала** — при 17 подписчиках Telegram ещё не показывает вкладку статистики/бустов в интерфейсе; реальный текущий уровень неизвестен до момента, пока пользователь не назначит бусты сам.
4. Нужны новые Railway-переменные: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION_STRING` — первые две пользователь получает сам на my.telegram.org.

## Библиотека
**Telethon** — зрелая, активно поддерживаемая Python MTProto-библиотека, `StringSession` удобен для хранения сессии как переменной окружения (не файл на диске, который бы конфликтовал с эфемерной файловой системой контейнера).
